At Chalk, I’ve been building a distributed query engine whose executor can target both CPUs and GPUs. For an early GPU demo, we compiled queries into cuDF operations and loaded their inputs from Parquet files. This made me wonder: how does cuDF read Parquet, and what controls does it provide for managing GPU memory? After all, the name of the game is keeping the working set as close to compute as possible.

I found a [paper](https://arxiv.org/html/2602.17335v1) discussing exactly my questions. I spent a morning diving deeper and getting my hands dirty. I later reran the experiments at 15 GiB of decoded data; the interactive figures retain the original smaller runs for comparison.

## A Brief Tour of Parquet

Before we talk about cuDF, it's important to understand at a high level how data is laid out in a parquet file. This will enable us to reason about how the encoded/compressed data is loaded from disk and placed in memory, and how the reader decodes the data into units that can be combined to create a desired batch/chunk size.

> Aside: confusingly, different libraries use chunk, batch, group, etc. to mean different things. I will try to disambiguate this by treating parquet's terminology as proper nouns.

Parquet files have two sections. They have a metadata footer that is written after all the data. This section contains the information needed to index into the first level of the data hierarchy called Row Groups and Column Chunks. It also could contain statistics and other information to select and prune Row Groups.

The section preceding the footer in the file contains all the data. The logical table represented by a parquet file is divided by rows into a Row Group. This is a horizontal partitioning of the data. Within a Row Group there are Column Chunks for each column in the data. Within a Column Chunk are Pages. These contain the bytes that should be decoded. Once a Column Chunk is loaded into memory, we can start decoding it Page by Page.

## cuDF's Parquet Reader

For our discussion, we will focus on how the reader manages compressed and decompressed data buffers for fixed-width tables, leaving nulls, nested data structures, and lists for another time.

The core algorithm for decoding parquet is fairly straightforward. The chunked reader groups selected row groups into input passes and loads their encoded column chunks. It then uses page metadata to plan subpasses for decompression and decoding. `pass_read_limit` influences this batching, but is a soft hint rather than a cap on total GPU memory. A separate control, `chunk_read_limit`, governs the size of returned output tables.

The GPU parallelism occurs in two main spots:

- Header kernels walk page headers within each column chunk, collecting information used to plan processing and allocate buffers. In this experiment, they assigned one warp per column chunk.
- Value-decoding kernels materialize the selected pages into output buffers. In the measured fixed-width decoding path, the launch assigned one block per data page.

## Experiments

Now that we know how the parquet reader works at a high level, we can see that the number of Pages and the Page size play a large part in determining performance. We ran two experiments. The first explored the results in Luo's paper regarding Page size. The second experiment held the Page size fixed to see how cuDF's parquet reader configuration led to different numbers of passes and sub-passes.

> The experiments were run on an NVIDIA RTX 3090 with 24 GiB of VRAM, using a C++ reader built against libcudf 26.10 on Ubuntu 20.04 under WSL2. Compatibility I/O was enabled; GPUDirect Storage was not used. Read timings included metadata processing, allocation, file access, transfers, and GPU decoding, ending with GPU synchronization. GPU aggregation was timed separately, and every measured sum was checked against a CPU reference. The [full experiment report](https://github.com/sanjayyepuri/cudf_scratch/blob/main/experiments/REPORT.md) includes reproduction instructions and raw results. Note the repository was generated with GPT-6.1 Sol.

### Sweep on Page Sizes

The larger Page experiment writes the same 15 GiB of non-null INT64 values into each of five files. Each has 60 Row Groups of 256 MiB, one Column Chunk per group, uncompressed PLAIN encoding, and no dictionary or statistics. Only the Page target changes. The chunked reader uses a fixed 2 GiB pass hint and releases each returned table after computing its sum.

This differs from the original 64 MiB whole-file experiment with four Row Groups. Encoded input, decoded output, and temporary buffers can exceed GPU capacity at the larger scale, so the read API and row-group layout also change. Compare Page sizes within each dataset; the figures preserve the original measurements as a separate selection.

Each Page layout has three unprofiled measured reads after an excluded warm-up, plus one separate profiled read after a warm-up. A 15 GiB file exceeds available host RAM, so the warm-up does not establish a warm filesystem cache. End-to-end timing includes file access and transfers.

At the largest Page size, this larger fixture launched **32 blocks per decoder launch**, across **30 decoder launches**. The original 64 MiB case had only four decoding blocks in one launch. The new reads recorded **1020, 1230 reader kernels**, depending on layout. These counts exclude reduction kernels. The former “33 kernels per read” observation applies only to the original whole-file experiment. Layout affects both work inside kernels and how the chunked reader batches that work. The timelines show recorded activity, not SM utilization, and gaps are not proof that the GPU is entirely idle.

### Memory Control

In the first experiment, I noticed that my parquet file was being decoded in a single pass and sub-pass. I wanted to see how the number of passes and sub-passes impacted performance. I understood that the additional overhead would increase the runtime, but I wanted to verify that the buffer memory used for reading the parquet was controlled.

The larger memory experiment uses 805,306,368 rows in 192 Row Groups and three flat integer columns: INT64 amount, INT64 customer ID, and INT32 quantity. The same distributions and 4,194,304-row group size as the original experiment now produce **15 GiB of numeric values**, stored in a **5.9 GiB ZSTD file** with a 1 MiB Page target. All three columns are decoded; only amount is reduced for the correctness check. I vary `pass_read_limit` from 256 MiB to 8 GiB with the output limit disabled, consuming and releasing each returned table individually.

The unlimited case is omitted at this scale. The original 640 MiB experiment peaked at roughly 2.9 times its decoded value size; extrapolating that ratio would exceed available GPU memory. This is a capacity estimate, not a measured out-of-memory result.

There are three baseline timing rounds per configuration after an excluded warm-up, one separate traced round after a warm-up, and two separate memory rounds after a warm-up. An RMM statistics adaptor tracked live allocations through the current device memory resource, including reader temporaries, output tables, and reduction allocations. The default CUDA allocator was preserved; no memory pool was added.

The 256 MiB hint used **96 input passes and 288 subpasses**; the 8,192 MiB hint used **3 input passes and 8 subpasses**. The smaller hint reduced peak live allocations from **8,189.96 MiB to 259.17 MiB**, while taking **3.1×** as long to read the file. The fastest measured configuration was **8,192 MiB**, at **3.348 s** and **8,189.96 MiB** of peak live allocations.

A practical comparison is 2 GiB versus 8 GiB: reader time falls from **3.690 s to 3.348 s** (about **9.3%**), while peak tracked allocations grow from **2.00 GiB to 8.00 GiB**. Most of the speedup is already present at the more moderate budget on this fixture; the fastest measured setting need not be the best use of memory for a larger query.

The primary 256 MiB–8 GiB grid targets practical working-set sizes. A separate completed 16–1,024 MiB timing sweep is retained as a diagnostic: 16 MiB is smaller than one compressed Row Group, so it is primarily a batching stress case, not a recommended setting. Its interrupted trace and unmeasured memory peaks are not used here. Changes across the primary grid can affect both input-pass and subpass counts; timing differences cannot be attributed solely to subpass count.

The 15 GiB dataset is processed incrementally; it is not retained as one 15 GiB GPU output table. This is why a much smaller live working set can suffice for this sum. A query that retains the entire output or uses additional operators has different capacity requirements.

Peak live RMM allocations count requests through the tracked allocator, including temporaries and output tables. They do not measure process-exclusive physical VRAM residency under WSL. These measurements also assume each returned table is released before the next is retained.

The refresh includes **18 unprofiled timing reads, six profiled reads, and twelve memory-instrumented reads** for the compressed fixture, plus **15 unprofiled and five profiled reads** for the Page sweep. Every measured read passed the CPU-reference sum, row-count, and selected-column checks. The memory runs also ended with zero tracked live bytes. The [large-scale methodology and reproduction commands](https://github.com/sanjayyepuri/cudf_scratch/blob/e401f781491dd2d18713f3df29c29b9073414c36/experiments/LARGE_SCALE.md) record the changed layouts, cache caveats, and omitted unlimited configuration.

## Closing Out

cuDF provides controls for trading reader memory against throughput, but those controls are soft hints rather than strict memory caps. In these experiments, we learned page layout affected the balance between header processing and value decoding, while the pass-memory hint affected batching and peak live allocations.

There are still many more details to be explored and a whole experimental parquet reader in the cuDF codebase. That's the next thing to look into. Until next time!
